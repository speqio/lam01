# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- `npm run dev` — start the Astro dev server (`astro dev`, default port 4321). Use `npx astro dev status` / `npx astro dev stop` to check or stop a background instance instead of guessing whether one is already running. Keystatic's admin UI is served at `/keystatic` on this same dev server — there's no separate CMS process.
- `npm run build` — production build (`astro build`). The search index (`/buscador.json`) is generated by the build itself, no extra step.
- `npm run preview` — serve the built `dist/` output locally.
- After `npm install`/`uninstall`, restart the dev server — Vite's dependency pre-bundling cache goes stale otherwise and serves old versions of changed packages.
- No test suite, linter, or formatter is configured in this repo — there's nothing to run beyond the build itself to catch errors. `npm run build` is the closest thing to a CI check (it fails on real TS/Astro errors), though it doesn't type-check as strictly as `astro check` would (not installed as a dependency; can be run ad hoc via `npx astro check` if deeper verification is needed, e.g. before a risky push).
- **Deploying is always `git push origin main`** — Cloudflare Workers Builds builds and deploys from the repo, and that is the only deployment route for this project. Before pushing: `git pull`, `npm run build`, `node scripts/verificar-keystatic.mjs` (a failed build freezes production silently, see below). Follow the deploy in Cloudflare → Worker → Builds. Do **not** deploy with `npm run deploy` / `wrangler deploy` from a local machine: it depends on a local OAuth token (which failed with `Authentication error [code: 10000]`) and can upload a stale `dist/` over what the client already published. The `deploy` script still exists in `package.json` but is not the route to use.
- `npm run cf:preview` — `wrangler dev`, runs the built Worker locally against the real Cloudflare runtime (Workers/Miniflare), closer to production than `astro dev` or `astro preview`. Useful for catching Cloudflare-runtime-only issues (see "Hosting migration" below) before deploying.
- `npx wrangler tail --format pretty` — streams live production logs from the deployed Worker. This is the fastest way to diagnose a 500 from `/keystatic` or any other server-rendered route, since Cloudflare's dashboard doesn't surface `console.error` output as immediately.

## Architecture

**Stack**: Astro 7 (hybrid static/server output via `@astrojs/cloudflare`) + React 18 islands (only for a couple of interactive pieces, see below) + Keystatic CMS (**GitHub mode** — commits directly to the repo via a GitHub App, admin UI at `/keystatic`, usable in production) + Markdoc for long-form content + Tailwind CSS 3 + GSAP 3.15. No test framework, no state management library, no custom server API routes beyond what Keystatic's integration injects — this is a static content site with a couple of client-side interactive components, not an app. One narrow exception to "GSAP only" for animation: `glitched-writer` (a small typewriter/glitch-text library) is used exclusively by the entrada reading-mode script — see below.

**Deployment**: Cloudflare Workers, deployed from the GitHub repo's `main` branch (`speqio/lam01`) via `wrangler deploy` (see `wrangler.jsonc`) — there's no separate staging branch/environment in this workflow. `output` is Astro's hybrid mode via the Cloudflare adapter, but in practice every route in this site is static-rendered via `getStaticPaths()` (see Routing below); the only routes that actually run server-side per-request are the ones `@keystatic/astro` injects (`/keystatic`, `/api/keystatic/*`), since GitHub-mode Keystatic needs a live server to talk to GitHub's OAuth/API. **This project was migrated from Vercel (Pages-style hosting) to Cloudflare Workers** — see "Hosting migration" below for what changed and what to watch for if repeating this elsewhere.

### Pages / route map

All routes live in `src/pages/`, one `.astro` file per route (no nested layouts beyond `BaseLayout`/`PostLayout`, no route groups):

- `/` (`index.astro`) — the home page; composes `HeroAnagram`, `HoverRevealHero` (latest número), the "últimas entradas" section (`ColeccionEstampillas.astro`, see below — the 16 latest entradas), `CategoriasCards`, and `ArchivoExplorer`, pulling from all four content collections in one frontmatter block.
- `/numeros` — grid of all números as **folders** (`CarpetaNumero.astro`, see below), with range-filter chips (inline `<button>`s, not `FilterChip.astro`; no JS filtering logic beyond a small inline toggle script that hides non-matching folders). This page is the only one that loads *every* entrada: it groups them by número with lookup maps built from the three collections, rather than the usual per-item `getEntry` (see "No joins" below) — hundreds of reads for the same handful of autores/categorías is the one case where that pattern doesn't apply.
- `/[slug]` — **entradas and números share one root route** (`src/pages/[slug].astro`, same URL scheme as the old WordPress site laantorchamagacin.com so links and SEO survive the DNS switch: `/nombre-de-la-entrada`, `/numero-01`; **no** `/entrada/…` or `/numero/…` aliases, one URL per content item). It only picks the view: `src/views/NumeroPagina.astro` / `src/views/EntradaPagina.astro` hold the markup. The build **fails on purpose** if a slug collides with a fixed page (`/archivo`, `/contacto`…), with another slug, or is the internal `sin-numero` (excluded from public routes). Never link to `/entrada/…`; link to `/<slug>`. A número page (`/numero-NN`): one número's detail page: uses `NumeroSequence.astro` for the entry listing (mobile carousel + desktop sequence, see below).
- `/categorias` — flat list of all categorías as filter pills, each linking to `/category/[slug]`.
- `/category/[slug]` (English `category`, to match the old site's URLs) — entries filtered by one categoría.
- `/autores` — list of all autores.
- `/autor/[slug]` — one autor's bio + their entradas.
- `/[slug]` (entrada view) — a single entrada's full content (rendered Markdoc), via `PostLayout.astro` rather than `BaseLayout.astro`. Ships an opt-in **"modo lectura"**: the page always loads in normal flow (full text, nothing hidden) with an "Entrar en modo lectura" button; clicking it locks the wheel/touch (`gsap/Observer`, `preventDefault` only while active — never before, or real scroll can never reach the activation point) and reveals one párrafo/verso at a time via `glitched-writer`'s typewriter effect, scoped to `#entrada-content` only (header/portada/galería/biografía stay in normal flow — an earlier attempt that locked the whole page broke the layout). A fixed "Salir del modo lectura" button is always present as the escape hatch (required before shipping any gesture-lock on mobile — see "Mobile vs. desktop" below). `prefers-reduced-motion` skips only the typewriter animation (instant text), not the paragraph-by-paragraph mechanism itself — earlier code fully disabled the whole feature under that preference, which silently broke it for any visitor with Windows' "Animation effects" setting off. The reading-mode container needs a higher `z-index` than `Header.astro`'s fixed nav (20) or its own wheel/touch listeners never receive events (hit-tested to whatever's on top). `PostLayout.astro`'s reading-progress bar is shared: during reading mode its width is set manually from `revealed/total` blocks (real scroll is locked, so its own scroll listener goes silent); exiting dispatches a synthetic `scroll` event to hand control back.
- `/archivo` — the full-catalog browse page; desktop renders `ArchivoHelix` (3D CSS spiral), mobile renders `ArchivoCascade` (CSS-only falling columns) — see "Mobile vs. desktop" below for why these are two separate components rather than one responsive one.
- `/proyecto` — static "about" prose page.
- `/contacto` — contact form. **No backend**: the `<form>` posts directly to `mailto:redaccion@blogliterario.com` (`method="post" action="mailto:..."`), so there's no API route, no email-sending service, and no server-side validation to maintain here — the browser's own mail client handles submission.
- `/keystatic` — the CMS admin UI, mounted by the `@keystatic/astro` integration; not a hand-written page. Runs server-side (GitHub mode requires a live OAuth/API round-trip to GitHub on every save), unlike every other route in this list.

### Content model

Four collections defined in **two places that must stay in sync**: `src/content.config.ts` (Zod schemas Astro uses to type/validate content) and `keystatic.config.ts` (the CMS field config that generates the editing UI and writes the files). Keystatic runs in **GitHub mode** (`storage: { kind: 'github', repo: { owner: 'speqio', name: 'lam01' } }`): saving an entry in `/keystatic` — in production or locally — authenticates via a GitHub App and commits the changed file(s) through GitHub's API. **Client saves go to the `keystatic` branch, not `main`** (`/keystatic` redirects to `/keystatic/branch/keystatic`, see "Branch workflow" below); only a merged pull request reaches `main`, which triggers the Cloudflare Workers build/deploy. There's no local-disk write path anymore. Requires three secrets to be present wherever Keystatic runs (`KEYSTATIC_GITHUB_CLIENT_ID`, `KEYSTATIC_GITHUB_CLIENT_SECRET`, `KEYSTATIC_SECRET` — see "Hosting migration" below).

- `autores` (`src/content/autores/*.json`) — `nombre` (also the slug field), `foto` (optional image), `biografia` (multiline text). No body/rich content.
- `categorias` (`src/content/categorias/*.json`) — just `nombre`. No image, no description — see `CategoriasCards.astro`'s cover-image workaround below.
- `numeros` (`src/content/numeros/*.json`) — `titulo` (slug field; conventionally `"Número N: Subtítulo"`, split at render time by `splitNumeroTitle()` in `src/lib/text.ts`), `fecha`, `portada` (required image), `descripcion` (optional).
- `entradas` (`src/content/entradas/*.mdoc`) — the only collection with body content, authored via Keystatic's rich-text `document` field (`contenido`, Markdoc under the hood). Frontmatter: `titulo`, `fecha`, `numero`/`autor`/`categoria` (Keystatic `relationship` fields, stored as the related item's slug string — a plain foreign key, not a join), `portada` (optional), `galeria` (optional array of images), `extracto` (short text used in listings/cards), `notas` (optional multiline text — footnotes/clarifications, rendered before `biografiaAutor`/`bibliografia`), `traducidoPor` (optional `relationship` with `autores` — see "Translator attribution" below).

**Images**: every `fields.image()` in `keystatic.config.ts` writes into a fixed `public/images/<collection>/` directory with a matching `publicPath` — e.g. entrada images land in `public/images/entradas/` and are referenced as `/images/entradas/...` in frontmatter. There's no image optimization/CDN step; whatever gets uploaded through Keystatic (or dropped in by hand) is served as-is.

**Images on the entrada page are shown unaltered (no crop, no color filter).** `EntradaImagen.astro` (individual images) and `EntradaGaleria.astro` (gallery) render each image at its natural size, capped by the column width and ~60–80vh of height: no fixed-aspect boxes with `object-cover` and no `grayscale`/`contrast` (unlike the cards in listings, which keep both on purpose). The gallery is a horizontal "strip" (native scroll-snap, one design for desktop and mobile, no nav buttons — the edges fade to the page background with `rgb(var(--color-canvas))` gradients that only show when there is more to scroll to that side, and a "01 / N" dial from `src/lib/dialNav.ts`) because editors upload images of mixed proportions; slides limit their width with `max-w-[100cqw]` (the scroller is a `container-type: inline-size`) so a wide image is never wider than the column. Do not stretch every image to one shared height: several uploads are small (e.g. 237×311) and would blur. Captions use `width: 0; min-width: 100%` so a long caption never widens the figure past its image. In reading mode the strip's images drop to `min(42vh, 400px)` (rule in `entrada/[slug].astro`) so strip + captions fit the 80vh block. Headless-browser check tip: Edge headless never goes below ~492px viewport width, so it cannot show a true 390px layout.

**Keystatic and images — read before touching content or images.** Saving from `/keystatic` sends GitHub one commit with "write these files / delete these files". Keystatic builds the delete list from the files an item had when it was opened, and GitHub rejects the whole save (`A path was requested for deletion which does not exist`) if any of them is not in the repo. A missing image is also read as an *empty* field and saved empty, so the reference is silently lost (`- {}` in a gallery, "Missing image" in the body). Three rules follow from reading Keystatic's own source (`node_modules/@keystatic/core/dist/keystatic-core.js`, image field: it slices the stored path by the length of `publicPath + slug + "/"`):
- **Path convention:** an item's images live in `public/images/<collection>/<slug>/<file>` and are referenced as `/images/<collection>/<slug>/<file>` (flat paths like `/images/numeros/numero-01-portada.JPG` break saving). Anything uploaded through Keystatic follows this on its own; content written by hand or by a script must too.
- **Every referenced image must exist.** Until the real files arrive, `node scripts/imagenes-pendientes.mjs quitar` removes references to missing files (cover, gallery items, standalone body images, author photos) and records them, with exact position, in `scripts/imagenes-pendientes.json`; `restaurar` puts them back once the files exist in `public/`. Números' `portada` is required, so `scripts/portadas-provisionales.mjs` generates a neutral "Portada pendiente" placeholder at the expected path (listed in `scripts/portadas-provisionales.json`; uploading the real cover from Keystatic replaces it).
- **Images cannot sit inside links** in the body (`[![](img)](url)`): Keystatic's document field only supports block images and refuses to open the entry ("Unknown inline node type: image"). Put the link in the surrounding text instead. **The same error also fires without any real image**, whenever a `!` ends up directly before a link — e.g. a WordPress-migrated footnote call `...democracia\![\[6\]](#_ftn6)`: Keystatic drops the `\` escape and then reads `![…](…)` as an inline image. Fix: one space between the `!` and the link. **While the `\` is still on disk the file is fine** — Markdoc parses `\![\[6\]](#_ftn6)` as text + link, and the editor opens it without complaint. The damage is done by Keystatic itself: every save re-serializes the whole body and drops the escapes (`[\[6\]]` → `[[6]]`), so a save made for an unrelated reason (uploading a cover) silently converts that paragraph into an inline image and the entry can no longer be opened — nor read by `createReader`, so the build and the `verificar` Action break too. That is why step 3 of `verificar-keystatic.mjs` flags the escaped shape as well: not because it is broken now, but because the next save will break it. Full write-up, with the upstream bug reports: `docs/keystatic-upstream.md`.

Run `node scripts/verificar-keystatic.mjs` before every deploy: it reads every item with Keystatic's own reader and checks every image path against the convention and against `public/` (exit code 1 on any problem). For editors: one item, one save — **the reload is now automatic**. After every successful save the panel shows a full-screen notice and reloads itself (`src/lib/adminReload.ts`, injected by `src/middleware.ts`; see "Auto-reload after saving" below), because Keystatic keeps the file list and the commit pointer from when the item was opened, so a second save without reloading tries to delete files the first save already removed. Reloading by hand (F5, or Ctrl+Shift+R) is still the fix if the notice ever fails to appear. Do not edit an item while a code push touches the same `.mdoc`/`.json`. Keystatic 0.6.9 is the latest release; patching its delete list was rejected because it would only hide the error while still losing image references.

**Branch workflow: content on `keystatic`, code on `main` (full detail: `docs/flujo-keystatic.md`).** `/keystatic` redirects (`src/middleware.ts`) to `/keystatic/branch/keystatic`, so the client's saves are commits on the `keystatic` branch, not on `main`. Content reaches `main` only through a pull request `keystatic` → `main` with the GitHub Action `verificar` (`.github/workflows/verificar.yml`: `npm run build` + `node scripts/verificar-keystatic.mjs`) green, merged with **squash**. `main` is protected in GitHub (PR + `verificar` required, owner bypass). Rules: code goes to `main`; do **not** touch `src/content` or `public/images` on `main` while a client cycle is open; after publishing code run `node scripts/keystatic-sync.mjs traer-main`; after squash-merging a PR run `node scripts/keystatic-sync.mjs cerrar-ciclo` (refuses if the client has unmerged saves), then tell the client to reload Keystatic. To undo a bad merge: `git revert` the squash commit on `main`, then `cerrar-ciclo`. The branch does **not** fix Keystatic's delete-list error (still: one item, one save — now with the reload automated, see below).

**Auto-reload after saving (`src/lib/adminReload.ts`).** In GitHub mode Keystatic never refreshes its own state after a successful commit — the local-storage path calls `setTreeSha(...)`, the github/cloud path does not — so `baseCommit`, `initialFiles` and `currentLocalTreeKey` stay frozen at the moment the item was opened and re-saving the *same* item fails ("This entry has been updated since it was opened", or GitHub's deletion error). A page load is the only reliable reset, so after every successful save the panel now shows a full-screen notice (the client's gradient animation, ported to pure CSS — no GSAP, because it must paint during the unload/load cycle) and reloads itself. It is injected into the `<head>` that `src/middleware.ts` already adds to the Keystatic page, so there's no new mechanism; the overlay removes itself when the panel has painted, with an 8s failsafe so it can never trap anyone, and if detection ever breaks the failure mode is "no reload", i.e. today's behaviour. Two things to know before touching the detection, both learned the hard way in production: **do not read the response body** (`res.clone()` rejects — urql aborts the request in its teardown, which cancels the cloned body branch), and **match the operation name `CreateCommit` in the request body**, not the GraphQL field `createCommitOnBranch`, which never travels in the request. Two diagnostic modes are kept behind a URL parameter, invisible to editors: `?aviso=prueba` mounts the overlay for 5s, `?aviso=registro` logs every GitHub/Keystatic request on screen and does not reload. This is mitigation, not a fix; the upstream one-liner is in `docs/keystatic-upstream.md` (§2, §6).

**A failed build freezes production, and the editor is not told.** Every Keystatic save is a commit to `main`; if that commit makes `astro build` fail, Cloudflare keeps serving the previous good version and every later save is silently unpublished until the build is fixed (read the build log in Cloudflare → Worker → Builds). The usual cause is a mismatch between the two schemas: a field the Zod schema in `src/content.config.ts` requires but Keystatic allows to be empty (Keystatic drops empty values, or saves an empty array slot as `- {}`). Rule: **anything Zod requires must be `validation: { isRequired: true }` in `keystatic.config.ts`** (today: `fecha`, `extracto`, `biografia`, número `portada`, and `imagen` of every gallery / individual-image item), so Keystatic refuses the save instead of breaking the deploy. As a second layer the gallery `imagen` fields are optional in Zod and `entrada/[slug].astro` skips items without an image. `node scripts/verificar-keystatic.mjs` reports empty required fields and empty gallery slots. Before any push to `main`: `git pull`, `npm run build`, `node scripts/verificar-keystatic.mjs`.

**Importing a new issue from WordPress (verified on números 27-31).** The WordPress export carries **no número information at all** — not in categories, not in tags, nowhere; the número↔post relation only ever existed in the *número index pages* of the old site (`paginaslam.xml`), and for issues newer than that export it exists only in the `.docx` index the magazine sends. Two things make the import reliable, and both were learned by getting them wrong first:

- **Assign the número by date block, not by matching titles.** Every issue was published on a single day, so the set of entries sharing a date *is* the issue, and the counts match the printed index exactly. Title matching across the whole collection fails in a way that looks fine: the index of número 28 writes the author above the title, so "Marcel Schwob / Petronio. Novelista" matched the entry `marcel-schwob-2` instead of `petronio-novelista`, both at 100%.
- **To read authorship off the index, match each piece only against the entries of ITS número** (8-15 candidates), never against all 339. That removes the whole class of collision above, and it is what let 75 of 75 pieces be matched with only 4 below 90% confidence, all four correct.

Each index has its own shape, so none of this is fully automatic: most mark the category before each piece, but a dossier (27) is bare título/autor pairs under a heading that has to be dropped or everything shifts by one, and a poetry showcase (29) uses the poet's name as the entry title. `scripts/migrate-wordpress.mjs` can still be reused to convert the HTML bodies — run it into a scratch directory, since it skips nothing when the target is empty — but it predates the current schema and writes `galeria` as a list of strings where each item is now an object with `imagen`; copying its output unfixed breaks the build. It also shifts the date one day forward on late-evening posts (timezone), consistently with the 318 entries already migrated.

**Two gaps in the números that are correct, not bugs.** `numero-05` **does not exist and must not be created**: the magazine confirmed the issue is extinct, so the jump from `numero-04` to `numero-06` is right. And `numero-27` has no images at all — the magazine has not produced them yet — so it is the one issue with no image zip.

**Content hygiene (migrated from WordPress).** Titles must be plain text: 32 titles once carried `<strong>`/`<em>` tags and they were stripped; if an import brings them back, strip them again (`</?[a-z][^>]*>`). Body text must not contain Keystatic's "Missing image <file>" placeholder lines or bare file names (`.jpg`/`.png`): they appear when an image file is missing at save time and were removed (only the Karl Kraus entry had them). The 75 demo entries and 8 demo autores were deleted before the DNS switch; the 4 WordPress entries in `sin-numero` (introduccion, la-madrugada-de-los-otros, la-construccion-de-una-palabra-…, sobre-tres-iconos-…) are kept and still need a real número/autor.

**Uploading images by hand from Keystatic (works, verified):** files land in `public/images/<collection>/<slug>/…` with the path Keystatic expects (a número's cover, a gallery item as `galeria/0/imagen.jpg`, body images by file name). Resize before uploading (≤1600 px on the long side and under 600 KB): the site serves images as-is, with no optimization step. **You don't have to do it by hand — `node scripts/optimizar-imagenes.mjs` does it** (report only; `--escribir` applies it), and step 6 of `verificar-keystatic.mjs` *fails* on anything over those limits, so an unoptimized upload is caught in the PR instead of reaching production. See "Image weight" below. Fill in the new "texto alternativo (SEO)" fields. Every save is one commit and one deploy, so group several images of the same entry into one save. Once an entry's images are done by hand, run `node scripts/imagenes-pendientes.mjs descartar <slug>` so a later `restaurar` does not add the originals on top (duplicates); `node scripts/imagenes-pendientes.mjs estado [slug]` shows what is still pending overall or for one entry. **Bulk migration of the remaining images is `scripts/migrar-imagenes.mjs`** — three subcommands, and the middle one is a deliberate decision point: `descargar` pulls every original from the old WordPress (still serving: the DNS has not switched) into a **staging directory outside the repo**, `optimizar` runs `optimizar-imagenes.mjs --escribir --raiz <staging>` there and reports the real post-optimization weight, and only `instalar` writes inside the repo — it copies the files into `public/` (never overwriting what is already there) and then calls `imagenes-pendientes.mjs restaurar`, which is what knows how to put each reference back in its original position. Staging is outside the repo on purpose: git history never releases a blob, so the weight is measured *before* anything is committed (that number is what decides repo vs. R2 — see `docs/imagenes-y-cms.md`). No new source material was needed: positions come from `scripts/imagenes-pendientes.json`, URLs from `scripts/migration-report/images-manifest.csv` (`ruta_local` has the same shape as the manifest's `ruta`, so the join is exact — measured: all 2.243 pending references resolve, 1.261 distinct files, 0 gaps). Two traps it already handles: the CSV stores URLs with HTML entities unresolved (`&amp;`), and two `ruta_local` values have no extension because they come from CDN URLs that do not end in a filename (`…/resize/540/540?…` → `540`) — the extension is taken from the response's real `Content-Type` and `instalar` fixes that path in the manifest. `descargar` is resumable and writes an auditable `scripts/migration-report/descarga-imagenes.json`.

**Image weight: `scripts/optimizar-imagenes.mjs` + step 6 of `verificar-keystatic.mjs`.** The site serves whatever is in `public/images` as-is (those files are outside Astro's asset pipeline), so nothing optimizes an upload on its way to the page. The 88 images in the repo were 39,3 MB, with 19 of them over 1600 px and one cover at 3436×4970 px / 3,1 MB for a ~700 px column; they were brought to **7,5 MB (−81%)**. The bulk migration from WordPress then added ~1.300 images: 411 MB of originals became **109 MB** in the repo (−73%), which is the number the repo-vs-R2 decision was made on — they stay in the repo (see `docs/imagenes-y-cms.md`). Run `node scripts/optimizar-imagenes.mjs` (report only) / `--escribir` (applies): long side ≤1600 px, EXIF orientation honoured, never enlarges (there is a real 311 px upload), never writes a bigger file, and steps quality down 80→72→64→55 only for the images that don't fit the cap. It is idempotent (skips anything it would improve by less than 10%), so re-running it generates no noise commits — **except for a file already over one of the caps**, where that 10% minimum is skipped, but only when the result actually lands *within* the cap: otherwise a file stuck at the quality floor would be rewritten on every run for a −1%, which is the exact noise the 10% rule exists to prevent. Without that exception a photo 1728 px on the long side could never be fixed at all (resizing it to 1600 gains under 10%, so the optimizer refused to touch it while step 6 kept rejecting it). Related: when a file is over the *dimension* cap the quality ladder also gets the original's byte count as its budget, because re-encoding a low-quality original at 80 can come out bigger, and the script never writes a bigger file. By default it **keeps the format and filename** so no reference has to be rewritten — every path must keep matching `/images/<collection>/<slug>/<file>` or Keystatic can't save the item. Two opt-in flags do rewrite references: `--webp-codigo` for the images Keystatic doesn't manage and only code refers to (`public/images/categorias/`, whose paths live in `CATEGORIA_IMAGENES` in `index.astro` — the `categorias` collection has no image field — and `public/images/home/`; those ten illustrations went 8,54 MB → 1,05 MB), and `--webp-png-sin-alfa` for PNGs with no *real* transparency, which are photos saved in the wrong format — note that having an alpha channel is not the same as using it, so a PNG that declares alpha is checked with `stats().isOpaque` before being skipped (29 images in the bulk migration carried a fully opaque alpha channel that only added weight). `--solo=<text>[,<text>…]` limits the walk to the paths containing those substrings, which is how a single image gets fixed without recoding the other 1.300 and filling the history with new blobs. **Step 6 of `verificar-keystatic.mjs` fails on any image over 600 KB or 1600 px** (the cap was 250 KB until a batch of número covers needed more: a cover is shown full-bleed in the home hero and in `/numeros`, not in the ~700 px reading column, so its budget is not the same as a body image's), which is what keeps this from degrading on its own; the `verificar` Action already runs it, so the check lives in the `keystatic` → `main` PR. Deliberate exceptions go in `scripts/imagenes-grandes-aceptadas.json` with a written reason; **it is empty today and should stay that way** — the five images the bulk migration left over the cap at 1600 px needed no hand cropping at all, four of them fit by dropping the long side to 1400 px and one grainy scan to 1100 px (`--escribir --lado=1400 --solo=<path>`). The long side is the lever, lowering quality is the last resort: the content is read in a ~700 px column, so 1400 px still leaves double density. Don't add `png({ palette: true })`: it is lossy quantization and, measured on those ten illustrations, gives byte-for-byte the same size as lossless. Full decision record, including why we did **not** move to R2 or EmDash: `docs/imagenes-y-cms.md`.

**Translator attribution.** `autor` is always the original authorship (unchanged meaning). `traducidoPor` is a separate, optional relationship to the same `autores` collection — both people must exist as real `autores` entries. Every page that resolves an entrada's `autor` for a card/header (`EntradaPagina.astro`, `index.astro`, `archivo.astro`, `category/[slug].astro`, `views/NumeroPagina.astro`) also resolves `traducidoPor` and passes it through as `translatorName`/a `traductor` lookup, rendered as a second line ("Traducción de X") below the "Por {autor}" line — `EntryCard.tsx`, `NumeroSequence.astro`, `UltimasEntradasCarousel.astro`, `EntradasCarousel3D.astro` all accept an optional `translatorName`. `autor/[slug].astro` gives **both** roles visibility: it lists entradas where the profile is either `autor` **or** `traducidoPor`, and resolves each card's real `autor` (not just the current profile) so a translator's page shows "Por {original author} · Traducción de {them}" correctly. No existing content was migrated to these two fields (see `docs/pendientes.md`) — they only apply going forward or when an editor fills them in by hand.

**No joins**: relationship fields are just slug strings. Every page that needs an entrada's related autor/categoria/número does the lookup itself with `getEntry('autores', entrada.data.autor)` etc., almost always via `await Promise.all(items.map(async (item) => ({...})))` since there's no batched/join query available in `astro:content`. This pattern repeats across `index.astro`, `archivo.astro`, `numero/[slug].astro`, `categoria/[slug].astro`, `autor/[slug].astro` — if you're adding a new listing page, this is the pattern to copy, not something to "optimize away" into a single query.

### Estampillas: the stamp collection and the número folders

Two components carry most of the site's current browsing UI. Both are newer than the card
language described further down, and new listings should reach for them first.

**`src/components/ui/ColeccionEstampillas.astro`** — a group of postage stamps, written
generic (it takes `items` shaped like `EntradaTicketItem` and nothing else) so it can be
dropped into any listing. Adapted from philately-gallery.framer.website. Things to know
before touching it:
- **The stamps are glued edge to edge** (`--aire: 0`), like an uncut sheet: the teeth of
  two neighbours form the single line of holes between them. They were tried overlapping
  with a tilt (read as a messy pile) and separated with a gap (read as loose cards).
- The teeth are `.estampilla-perforada` (`global.css`, four edge layers + `mask-composite:
  intersect`), applied to the **face**, not to an inner layer — applied inside, the card's
  own background stayed uncut and showed around the photo as a badly cropped frame. Not
  `EstampillaFace.astro`'s mask, which tiles holes across the whole surface.
- `disposicion`: `hoja` (grid on desktop, scroll-snap strip on small screens), `tira`
  (one horizontal row at every width) or `columna` (one vertical row). The last two render
  the pagination dial (`lib/dialNav.ts` classes; the dial's own script lives in the
  component and works on both axes).
- **Choosing a stamp pulls it out of the sheet**: it is *moved in the DOM* into a fixed,
  centred stage while the page goes behind a blurred backdrop, with its ficha read beside
  it (below it on small screens) as plain text, no panel. Moving it is required, not
  decorative: a `fixed` element inside a transformed ancestor resolves against that
  ancestor instead of the viewport. **Never animate `transform` on an ancestor of a
  `.coleccion` root** for the same reason. The jump is hidden with a FLIP, and the size
  must be set *before* measuring (inside the stage the stamp would otherwise measure the
  whole viewport and fly in from a corner). The return is measured live, not replayed from
  the opening delta.
- No `IntersectionObserver` here, unlike the site's other heavy components: a collection
  can be born inside a closed folder, which never intersects, and would never initialise.
  Clicks are delegated per root and Escape is a single page-level listener — `/numeros`
  mounts about thirty of these.
- No hover effects, by request: everything happens on click/tap.

**`src/components/ui/CarpetaNumero.astro`** — the `/numeros` folder. A flat dark file
folder drawn entirely in CSS (no assets), with the número's portada full-bleed behind a
dark bottom gradient. The gradient and its text are **literal black/white, not tokens**:
in light theme the tokens invert and the scrim turned white, leaving the title unreadable
over the photo. Three states, not two: closed → open (the stored stamps fan out of the
top; CSS `:hover` where there is hover, first tap where there isn't) → the blurred stage
with that número's sheet of stamps. The state is cleared when the stage opens *and* when
it closes, or the folder stays fanned out behind the backdrop and reappears that way.

### Design system

`tailwind.config.mjs` defines **semantic** color tokens rather than literal palette names — component code should reference the role, not a hardcoded color, since the token values are what get swapped on a re-theme:

| Token | Value | Role |
|---|---|---|
| `canvas` | `#121212` | Page background |
| `surface` | `#292929` | Elevated surfaces: cards, modals, nav bars |
| `ink` | `#ffffff` | Primary text/foreground |
| `ink-muted` | `#a0a0a0` | Secondary text, metadata |
| `bone` | `#d0d0d0` | Long-form prose body text |
| `accent` | `#a6294a` | The **only** signal color — CTAs, tags, active borders. Deliberately singular (see the comment in `tailwind.config.mjs`): new UI should not introduce a second "decorative" color alternating with accent, only use accent as the one highlight against surface/canvas/ink. |

`fontFamily.{sans,serif,mono,headline}` all currently map to the single Lekton font — the four role names are kept so a future typography change only touches this one file, not every component's class list.

`src/lib/cardStyles.ts` (older language, kept for the pages that still use it) centralizes the Tailwind classes for the "entry card" anatomy (image on the left with an overlaid category badge, text on the right) that recurs across `EntryCard.tsx`, `NumeroSequence.astro` and `UltimasEntradasCarousel.astro` — reuse these rather than re-deriving the layout in a new component. `cardBadge` alone (solid accent background, canvas text) is reused well beyond that specific anatomy too — `EntradasCarousel3D.astro`, `ArchivoCascade.astro`, `CategoriasCards.astro` — since the badge itself is independent of where the image ends up mounted. `cardShell` is deliberately *not* where the reveal-on-scroll hook (`entry-card-reveal`, see below) lives — `numeros.astro` reuses `cardShell` as static markup with no reveal script, so that class only goes on `EntryCard.tsx`'s own `<a>`, not into the shared constant (putting it there once hid `/numeros`' cards forever, since nothing there ever un-hides them; that page now renders folders, but the trap is the same anywhere `cardShell` is reused as static markup).

`src/lib/dialNav.ts` centralizes the Tailwind classes for the "01 / N" pagination dial (thin track + proportional thumb + counter) used by `NumeroSequence.astro`'s mobile carousel and `CategoriasCards.astro`'s fan — only the classes live here, the scroll/drag-driven JS that moves the thumb stays in each component since it depends on that component's own scroll/position source.

`src/lib/text.ts` exports two helpers worth knowing before writing new UI text:
- `normalizeTitleText` sentence-cases a title in JS instead of relying on CSS `text-transform: uppercase`. This exists because on some mobile browsers, uppercasing an accented character via CSS breaks the glyph composition with this font and silently drops the accent (e.g. "reseña" renders "RESENA"). Any new UI that displays a title/category name in caps should follow this pattern rather than reaching for `uppercase` in Tailwind.
- `splitNumeroTitle` splits a número's raw `titulo` on `:` into `{titulo, subtitulo}`, each independently run through `normalizeTitleText`. Used wherever a número's title/subtitle need independent styling (home hero, `/numero/[slug]`).

### Copy language: español neutro

All interface copy (buttons, headings, hints, empty states, meta descriptions — anything the site itself generates) is written in neutral/standard Spanish, not Argentine voseo ("explora" not "explorá", "tu"/"ti" not "vos"). This does **not** apply to the literary body text inside `entradas` content files (`.mdoc`) — those are authored pieces with their own voice and are left as written. When adding new UI strings, write them in neutral Spanish from the start.

### Animation: GSAP only

GSAP is the sole animation/interaction library across the codebase (no Framer Motion, no Three.js — both were removed at some point; don't reintroduce either). Recurring idioms worth knowing before adding a new interactive component:

- **`Observer`** (from `gsap/Observer`) for wheel/touch/pointer gesture capture, always targeting the specific interactive element rather than `window`, so the gesture doesn't hijack page scroll when the user isn't directly over the component. Almost every carousel/draggable component in the site (`NumeroSequence`, `UltimasEntradasCarousel`, `ArchivoHelix`, `CategoriasCards`) uses `Observer` with separate `type: 'wheel'` and `type: 'touch,pointer'` instances rather than raw DOM event listeners.
- **`gsap.quickTo`** for "chase a moving target" easing (e.g. a value that snaps toward wherever the user last dragged to) instead of a hand-rolled `+= (target - current) * factor` lerp — framerate-independent and can be re-targeted every frame without restarting.
- **`gsap.ticker.add(fn)`** instead of a raw recursive `requestAnimationFrame` loop for anything that needs continuous per-frame updates (e.g. `ArchivoHelix`'s ambient spiral drift).
- **`ScrollTrigger`** with `once: true` for simple reveal-on-scroll (see `EntryCard.tsx`). The hidden initial state (`opacity:0`, `translateY(24px)`) is set by CSS (`.entry-card-reveal` class, rule in `global.css` gated on `html.js` + `prefers-reduced-motion: no-preference`), never by a `gsap.set()` inside the component's effect — `EntryCard.tsx` is a `client:visible` React island, so hydration can lag well behind first paint; if JS set the hidden state, an already-painted, fully-visible card would visibly snap to hidden before animating back in. `BaseLayout.astro` adds the `js` class to `<html>` synchronously in a blocking `is:inline` `<head>` script (same pattern as the dark/light theme flash-prevention script right above it) so the hidden CSS rule is in effect before the very first paint; no-JS visitors never get the `js` class, so cards simply render complete. This is the general rule for any future entrance animation: put the *hidden* starting state in CSS gated behind a pre-paint JS marker, and let the animation library only ever reveal, never hide, what's already on screen.
- **`Draggable`** (from `gsap/Draggable`, `type: 'rotation'`) + **`InertiaPlugin`** for a drag-to-spin wheel/carousel (see `EntradasCarousel3D.astro`, desktop only). Both ship free in GSAP's core bundle — no club/membership needed. Unlike `Observer`, `Draggable` in `rotation` mode needs to track pointer movement in any direction to compute the angle, so it can't be restricted to one axis the way `Observer`'s wheel/touch handlers can — treat it as desktop-only rather than trying to make it coexist with mobile page scroll (see below).
- A recurring geometric pattern for "wheel" carousels (`UltimasEntradasCarousel`, `ArchivoHelix`, `CategoriasCards`): a single `pos.value` number, a `shortestDistance(index, position, total)` helper that computes each item's signed circular distance from that position (enabling infinite wraparound), and a `render()` function that maps each item's distance to its transform (rotation/x/y/opacity/z-index). Dragging updates `pos.value` 1:1 with no easing; releasing hands off to `gsap.quickTo` for an eased/inertial snap to the nearest integer position. If you're building a new "spin through N items" component, this is the pattern to reach for rather than inventing a new one.
- Each interactive component registers only the GSAP plugins it needs via `gsap.registerPlugin(...)` at the top of its own `<script>`/module — there's no shared central GSAP setup file.
- Heavy interactive components defer their own init with an `IntersectionObserver` (`rootMargin: '200px'`) rather than running setup code unconditionally on page load — this is a hand-rolled equivalent of React's `client:visible`, used consistently in the non-React (`.astro` + `<script>`) components since they don't have that directive available.
- Avoid `back.*` eases (`back.out`, `back.inOut`) for entrance animations that run on first page load, e.g. the home hero — they deliberately overshoot past the target and bounce back, which reads as a jarring "jump" rather than a smooth settle, worst on the very first thing a visitor sees. `HeroAnagram.astro`'s letter-flip animation used `back.inOut(1.7)`/`back.out(1.7)` for this reason and was switched to `power3.inOut`/`power3.out` (direct, no overshoot).

### Mobile vs. desktop are often genuinely different components

Several sections of the site (e.g. the entry listing on `/numero/[slug]`, `/archivo`) do **not** share one responsive implementation between breakpoints — mobile and desktop are separate components/code paths, toggled via Tailwind `md:hidden` / `hidden md:block` wrappers, with each script also self-gating on `window.matchMedia('(min-width: 768px)')` before doing any setup work. This is deliberate: a gesture-capturing mechanism (wheel/touch capture, `preventDefault`) that's safe on desktop (the user can always move the mouse off the element to get scroll back) can permanently trap a mobile user who has no equivalent escape gesture. When touching one of these sections, check which breakpoint's code path you're actually meant to be editing.

Not every interactive component needs this split, though — `CategoriasCards.astro`'s fan carousel runs identically on both breakpoints, because its gesture capture is `Observer`-based and axis-constrained (horizontal drag/wheel only, `touch-action: pan-y` lets vertical page scroll pass through untouched). `EntradasCarousel3D.astro`'s `Draggable`-rotation carousel was tried unified across breakpoints once and reverted back to desktop-only after it interfered with scrolling on real mobile devices — the axis-unconstrained nature of rotation dragging is the difference-maker, not just "is it 3D" or "is it draggable." When building a new gesture-driven component, that's the question to ask before assuming it can be a single cross-breakpoint component.

The other recurring mobile-safety pattern is **CSS-only, zero-JS-gesture components on mobile where desktop gets something heavier**: `ArchivoCascade.astro` (mobile counterpart to `ArchivoHelix`'s 3D spiral) is pure `@keyframes` looping columns with no `<script>` at all — it structurally cannot trap a gesture because it never listens to one. When a desktop interaction is too heavy/risky to bring to mobile as-is (perf or gesture-trap concerns), a declarative CSS-only alternative is the established fallback, not a stripped-down JS version of the same mechanic.

### Search

The header/mobile search (`src/components/ui/SearchModal.tsx`, a React island in `Header.astro` and `MobileFloatingNav.astro`) does **not** use full-text search. It loads `/buscador.json` (generated at build by `src/pages/buscador.json.ts`: entradas, autores, categorías and números — names/titles only, no body text, no fixed pages) once when opened and filters in the browser: accent/case-insensitive, prefix matches first, max 8 results, min 2 characters, arrow keys + Enter. Each result shows a type label (Entrada/Autor/Categoría/Número) and title (entradas add "Por autor" and, if translated, "Traducción de X"), never an excerpt. An entrada also matches when the query hits its translator's name (`traducidoPor`), not just its title — same idea as `EntryCard.tsx`'s translator line. `autores.esTraductor` (checkbox in Keystatic) swaps an autor result's label from "Autor" to "Traductor" — purely a display flag, independent of whether that person is set as `traducidoPor` anywhere. Pagefind was removed. Because entradas/números now live at the site root, `buscador.json` is a reserved slug in `src/pages/[slug].astro`.

### Navigation

`src/data/navItems.ts` is the single source of truth for the main nav — both `Header.astro` (desktop top bar) and `MobileFloatingNav.astro` (mobile fixed bottom bar, with active-route highlighting via `Astro.url.pathname`) map over the same list rather than hardcoding links twice.

### Routing

Dynamic routes (`autor/[slug]`, `category/[slug]`, and the root `[slug]` for entradas + números) all use `getStaticPaths()` over the relevant `astro:content` collection — this is a fully static-path site per content item, not server-rendered per-request page content, despite the Cloudflare adapter technically supporting hybrid/server rendering.

## Hosting migration: Vercel → Cloudflare Workers (+ Keystatic local → GitHub mode)

This project was originally deployed on Vercel with Keystatic in `local-storage` mode (edit locally, `git push`, Vercel auto-builds). It was migrated to Cloudflare Workers with Keystatic in `github` mode (edit from `/keystatic` in production, saves commit directly to GitHub, which triggers the same build). Both changes were done together but are logically independent — you could adopt either one without the other.

### What actually changed

- **Adapter swap**: `@astrojs/vercel` → `@astrojs/cloudflare` in `astro.config.mjs`. Mechanical in principle, but see gotchas below — it wasn't a drop-in swap in practice.
- **Astro core bump**: `astro@^7.2.7` → `^7.3.2`. The installed `@astrojs/cloudflare@14.x` calls a `renderForPrerender` export that didn't exist yet in the older Astro patch — the peerDependencies range (`astro: '^7.2.0'`) didn't catch this because peer ranges lag behind what a package actually needs at the API level. **Lesson: when a fresh adapter install throws a `MISSING_EXPORT` error, try bumping the framework to its latest patch before assuming the adapter is broken.**
- **New `wrangler.jsonc`** at the repo root — minimal config (`name`, `main: "@astrojs/cloudflare/entrypoints/server"`, `compatibility_date`, `compatibility_flags: ["nodejs_compat"]`). Cloudflare/Astro deprecated Pages support for this adapter sometime before this migration — **the adapter's own docs still describe a Pages flow in older cached versions, so verify against the currently-installed version's actual behavior (a real `npm run build` + `wrangler deploy --dry-run`), not just what a search engine or cached doc page says.** The equivalent of "connect the repo, auto-deploy on push" is now **Workers Builds** (Cloudflare dashboard → Worker → Settings → Builds → Connect), not the old Pages dashboard flow.
- **`package.json` scripts**: added `deploy` (`wrangler deploy`) and `cf:preview` (`wrangler dev`). The `build` script (`astro build && pagefind --site dist/client`) needed **no change** — the `dist/client` / `dist/server` split is Astro's own convention whenever any adapter is present, not something Vercel-specific, despite how it looks from the outside.
- **Keystatic packages bumped**: `@keystatic/core@0.5.51 → 0.6.9`, `@keystatic/astro@5.2.0 → 6.0.0`. Necessary, not optional — the older version's GitHub-mode server code read `Astro.locals.runtime.env` to get at secrets, which Astro removed in v6 in favor of `import { env } from 'cloudflare:workers'`. Keystatic's own bundle hadn't caught up in the version this project started on, and it failed **silently into a 500 with an unhelpful stack trace** rather than a clear "unsupported version" error — `npx wrangler tail --format pretty` while reproducing the failing action in a browser was what surfaced the real cause.
- **`keystatic.config.ts`**: `storage: { kind: 'local' }` → `storage: { kind: 'github', repo: { owner: 'speqio', name: 'lam01' } }`.
- **Three new secrets**, set via `wrangler secret put <NAME>` (never committed, never put in `wrangler.jsonc`): `KEYSTATIC_GITHUB_CLIENT_ID`, `KEYSTATIC_GITHUB_CLIENT_SECRET` (both from a GitHub App created for this purpose — see below), `KEYSTATIC_SECRET` (a random value generated locally, e.g. `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"`).
- A **GitHub App** (not an OAuth App) was created manually in the GitHub UI, scoped to this repo only, with `Contents: Read & write` and `Metadata: Read-only` (the only option — GitHub doesn't offer write access to Metadata at all, it's unrelated to page-level SEO meta tags despite the name overlap). Its callback URL is `<production-origin>/api/keystatic/github/oauth/callback` — confirmed against Keystatic's own bundled source (`grep -r "oauth/callback" node_modules/@keystatic/core/dist/`) rather than trusting incomplete official docs on this specific point.
- **`.gitignore`**: added `.wrangler/` (Miniflare's local dev/state cache) and any local dry-run scratch dirs, alongside the pre-existing `.vercel/`.

### Best practices for repeating this migration elsewhere

1. **Don't trust cached/generic docs for a fast-moving adapter.** Both the Cloudflare and Astro ecosystems change their recommended deployment model faster than search results and even official doc pages (which can lag behind the exact npm-published version) keep up. Before configuring anything by hand, run the actual installed version's dry-run/build and read *its* output and error messages — they're more current than any doc fetch. When docs and installed behavior disagree, the installed package wins.
2. **Verify exact API paths/behavior in `node_modules` when docs are silent or vague**, especially for anything security-sensitive like an OAuth callback path — a wrong guess there fails opaquely (GitHub shows a generic "redirect_uri is not associated with this application" error that doesn't point at the fix).
3. **Never put secrets in a config file that gets committed.** Use the platform's secret-store command (`wrangler secret put`, Vercel's `env add`, etc.) exclusively. If a secret is accidentally pasted in plaintext anywhere (chat, terminal history, a file), treat it as compromised and regenerate it rather than trying to "undo" the exposure.
4. **Distinguish a platform-level fingerprint/identifier from the actual secret value.** GitHub (and similar dashboards) sometimes display a hash/fingerprint of a secret for identification in a list view, which looks superficially like a credential but isn't usable as one — the real value is only shown once, at generation time.
5. **Sequence a hosting migration in two independently-verifiable phases**: (a) swap the adapter and confirm the *existing* app behaves identically on the new host, *then* (b) layer on any CMS/backend mode change (like Keystatic's storage mode) on top of a host you've already proven works. Debugging is much harder when both the hosting platform and the CMS's runtime assumptions change in the same untested step.
6. **Watch for a stale git integration on the old host.** If the old platform (Vercel, in this case) is still connected to the same branch, it will keep trying to rebuild on every push and may fail loudly (missing adapter, etc.) once the new adapter lands — decide explicitly whether to disconnect it, let it fail intentionally during the cutover window, or keep it as a working fallback a little longer, rather than being surprised by a "build failed" notification.
7. **When a serverless/edge runtime throws a vague, generic-looking stack trace (a 500 with no clear message in the browser), go straight to the platform's live log tail** (`wrangler tail`, Vercel's `vercel logs`, etc.) **while reproducing the action**, instead of guessing from the client-side symptom alone — the real error (in this case, a removed Astro API a dependency still relied on) is almost always only visible server-side.
8. **A dependency needing a bump isn't always the one you just touched.** The root cause of the 500 here was in Keystatic, a package this migration didn't intend to touch at all — it only surfaced because the *adapter* swap changed which runtime API was available. When adopting a new adapter/host, be ready to also update anything else in the dependency graph that talks to that host's runtime directly (CMSs, auth libraries, anything with its own server-side integration code), not just the adapter itself.
